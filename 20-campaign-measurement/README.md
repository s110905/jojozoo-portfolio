# 活動成效量測機制：把廣告點擊接到現場到場

[返回作品集總覽](../README.md)

### 售票平台不回傳訂單時，自己在活動流程裡埋量測點，讓每一檔活動都算得出「人從哪裡來、來了多少」

> 兩檔實測：2026 年 9 月周年慶以現場來源問答取得來客來源占比（回答率 72.6%）；10 月萬聖活動每一組登記都帶來源，並在兩個活動日由現場人員核實到場人數。

## 問題：廣告後台只看得到點擊，看不到人有沒有來

園區的購票走第三方平台，訂單與營收不會回傳。廣告後台能回答的只到「多少人點了、多少人進站」，接下來就斷線：

- 進站的人有沒有真的來園區，沒有資料。
- 現場的人是看到廣告、官網、朋友分享，還是路過，沒有資料。
- 檔期結束後要檢討預算，只能拿點擊成本當成效。

等售票平台開放資料不是短期能解的事，所以改成在自己掌握得到的環節補量測點：活動頁、LINE 登記、現場報到。

## 做法一：現場來源問答（周年慶尋 4 大作戰）

[周年慶集點活動](../14-anniversary-find-four)不需要事先登記，遊客到場掃 QR 就能玩。量測點放在開始集點之前：先選「從哪裡知道這個活動」，再進入掃碼。

- 選項固定為 FB 廣告、IG 廣告、官網、朋友分享、現場看到，方便跨日期比較。
- 回答跟著參加者紀錄存進資料庫，可依日期區間重新統計。
- 回答率一併記錄，知道這份占比代表多少參加者。

9 月 12–13 日兩天的結果（回答率 72.6%）：

| 來源 | 9/12–13 占比 | 8/29–9/11 累計占比 |
| --- | ---: | ---: |
| 現場看到 | 50.9% | 70.2% |
| FB 廣告 | 19.3% | 9.6% |
| 官網 | 14.1% | 11.6% |
| 朋友分享 | 12.3% | 6.2% |
| IG 廣告 | 3.4% | 2.3% |

FB 與 IG 廣告合計由 11.9% 升到 22.7%。這是遊客自己回答的來源，可以看出兩段期間的來客結構不同，但沒有對照組，不能直接說成廣告帶來多少購票者。

## 做法二：來源跟著登記走到現場報到（萬聖活動）

萬聖活動改成要先登記、領邀請券才能參加，因此可以把來源綁在每一張券上，不必靠遊客回想。

```text
廣告、官網、社群貼文的連結（帶來源參數）
  │
  ├── 官網活動頁：跨頁保留來源，帶到 LINE 登記入口
  ├── LINE 登記：選參加日期、填同行大人與小孩人數，來源寫入邀請券
  ├── 現場報到
  │     ├── 工作人員核實：填實際到場的大人與小孩
  │     └── 入口 QR 自助報到：遊客自行申報，另外存放
  └── 戰情室每小時彙總：依來源、參加日期、登記日期拆解
```

- **來源不靠人工對照**：連結帶的平台與來源在登記當下寫進邀請券，廣告來的券還會保留是哪一則廣告。
- **登記與到場分開記**：登記時填的是預計人數，報到時填的是實際人數，兩者不混用。
- **同一份資料多種切法**：同一批券可以依參加日期、登記日期或來源重新彙總，檔期中就能看哪個入口在帶登記。
- **廣告花費放在同一頁**：戰情室把廣告花費、進站與登記並排，檔期中就能換算每組登記的成本，不用等結案再對表。

活動結束後，這套機制可以直接產出下列數字（實際人數屬營運資料，這裡不公開）：

| 產出 | 說明 |
| --- | --- |
| 登記組次與去重帳號 | 同一帳號登記兩天算兩組、一個帳號 |
| 登記時預計人數 | 大人與小孩分開 |
| 現場核實到場 | 報到組次，以及實際到場的大人與小孩人數 |
| 各入口的登記與到場 | 依廣告、官網、社群貼文等來源拆解 |
| 未登記的現場發券 | 人工登錄，另列 |

登記來源組成（占全部登記組次）：

| 登記入口 | 占比 |
| --- | ---: |
| FB／IG 廣告 | 33.3% |
| FB 自然貼文 | 30.1% |
| 官網 | 18.9% |
| 沒有帶到來源 | 13.7% |
| Threads、LINE、Google 地圖、現場 | 4.1% |

## 避免把數字算錯的設計

量測機制最容易出問題的地方是口徑，這幾項是做進系統裡的：

- **測試券排除**：依券號標記測試資料，彙總時排除，並顯示排除了幾張。
- **抓不到資料不當成零**：讀取失敗、資料過期或格式不符時顯示未知，避免把「沒抓到」看成「沒人來」。
- **組次與帳號分開**：同一個帳號可以登記兩天，所以登記組次和去重帳號各算各的，各來源的帳號數也不直接相加。
- **核實與自助分開**：工作人員核實與遊客自助申報存在不同的表，同一張券可能兩邊都有，不相加當成總到場人數。
- **沒登記的人另外記**：現場臨時發的券系統裡沒有，改用人工登錄檔並標明來源，不混進報到人數。

## 兩種做法怎麼選

| | 現場來源問答 | 來源跟著登記走 |
| --- | --- | --- |
| 適用活動 | 到場就能參加、不需事先登記 | 需要事先登記或領券 |
| 來源怎麼來 | 遊客自己回答 | 連結參數自動帶入 |
| 能回答的問題 | 現場的人從哪裡知道活動 | 每個入口帶來幾組登記、其中幾組到場 |
| 主要限制 | 靠記憶，只涵蓋有回答的人 | 沒帶參數的入口會落在「未知」 |
| 建置成本 | 低，加一個問題即可 | 較高，需要登記、報到與彙總三段 |

有登記流程的活動優先用第二種，資料可以逐組追到到場；免登記的現場活動用第一種，成本低、當天就有結果。兩種都做得到的時候可以併用，用問答去補沒有帶到來源的那一塊。

## 限制

- 兩種做法量到的都是登記與到場，沒有訂單與營收，不能換算成 ROAS。
- 沒有對照組，來源占比不等於廣告造成的增量。
- 來源記的是登記當下的入口。先看到廣告、之後從官網登記的人，會算在官網。
- 萬聖活動有 13.7% 的登記沒有帶到來源；核實到場只計工作人員完成的報到，自助申報不併入。

## 技術與協作

- LINE LIFF、Cloudflare Pages Functions、Supabase PostgreSQL：登記、邀請券與報到。
- Next.js、Cloudflare Workers、Cloudflare D1：集點活動與來源問答。
- WordPress 自訂程式片段：官網跨頁保留來源參數。
- Node.js 排程：每小時彙總登記資料並產生戰情室頁面，附自動測試檢查口徑。
- Meta Marketing API、GA4：廣告花費與進站資料。

AI 協助實作、撰寫口徑測試與核對彙總結果；量測定義、現場流程與數字的對外說法由人員確認。
